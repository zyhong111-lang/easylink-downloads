# EasyLink 项目规则：代码修改、测试与回归保护

> **执行适配说明（2026-10-28）**：本文件是 EasyLink 各仓库统一测试与回归基线，不授予任何服务器访问、部署、构建或生产改动权限。各仓库现有 AGENTS.md 的 SSR 生产保护、平台专属构建限制（例如 iOS 本地优先、Web 仅 .6 构建）、已获批准的测试流程与更严格的安全边界继续有效。冲突时先遵守更严格的安全与发布边界，不能兼顾的测试标记 NOT RUN 并报告，不得伪造 PASS；需要变更既有具体规则时须取得用户明确许可。

> 适用范围：EasyLink 网站、后台 API、会员/支付、SSM 节点管理、iOS、Android、PC 客户端、SEO、部署脚本及基础设施。
> 执行主体：Codex 及其他开发代理。除用户明确批准的例外外，所有代码变更均遵守本规则。
> 第一原则：**修复一个问题，不得以破坏已正常运行的功能为代价。验证通过不等于允许发布。**

## 1. 修改前：先确认边界和基线

1. 读懂需求，明确：目标行为、验收标准、涉及模块、明确不允许改动的模块。需求不明时采取最小安全变更，不擅自扩大范围。
2. 检查 Git 状态、当前分支、基线提交、工作区未提交改动及部署配置。**不得覆盖、丢弃或混入他人未提交的改动**。
3. 搜索相关调用链、API 契约、数据库字段、配置、客户端依赖和现有测试，形成“影响清单”；特别检查登录、会员确权、到期/续费/撤权、SSM 授权、VPN 连接与断线重连等横向依赖。
4. 修改前运行可执行的相关现有测试，记录原始通过/失败情况；无法运行的项目、原因和验证缺口必须如实披露。不得把原有失败伪装成此次变更引入，也不得以“原来就失败”掩盖新增缺陷。
5. 在独立功能分支和 PR 中工作。没有用户授权，不得直接修改主分支、测试服务器或正式环境。

## 2. 修改中：最小改动，保持契约

1. 只修改实现本次目标所必要的代码。**禁止顺手重构、批量格式化、更新无关依赖、修改无关文件或覆盖整份配置**。确需扩大范围，先列出原因、风险和拟改文件，取得批准。
2. 保持原有外部行为和兼容性：API 路径/请求/响应、错误码、会员有效期与授权规则、支付回调、配置键、数据库 schema、客户端所依赖的数据结构。需要破坏性变更时，制定版本兼容、迁移和回滚方案，未经批准不得执行。
3. 数据库变更优先采用可兼容的扩展—迁移—清理顺序；涉及批量更新、数据删除和不可逆迁移时，必须先确认备份、恢复方式和授权。
4. 涉及会员、SSM、付款、Webhook、重试、并发及超时，明确幂等、顺序、异常恢复与重复消息处理。不能仅凭单次成功判断流程正确。
5. 严禁将真实密钥、访问令牌、用户个人数据或生产连接信息写入测试代码、日志、报告和仓库。
6. 不得为了让 CI 变绿而删除测试、弱化断言、跳过失败用例、禁用门禁或直接修改测试预期来迎合错误行为。业务规则经批准变更时，才允许同步修订预期。

## 3. 测试先行：新功能和 Bug 都留下回归保护

1. **Bug 修复**：优先先写能够重现问题且在修复前失败的测试（红），再修复使之通过（绿），最后执行相关回归。确实无法自动复现时，说明原因并保留可复验的手工步骤/证据，后续尽可能自动化。
2. **新功能**：至少覆盖正常路径、关键边界条件、错误/超时/重复请求、权限及兼容性；新增的可靠自动化用例纳入回归集。
3. **回归固化**：将稳定、可重复、断言明确的关键用例保存在仓库，并接入 CI；优先覆盖历史故障、核心业务和跨模块接口。不是所有临时调试脚本都需要固化。
4. 测试分层：单元测试（规则/函数）→ API/契约测试（请求与兼容）→ 集成测试（DB/SSM/支付沙箱等）→ 关键端到端测试（真实登录、确权、连接、续费/撤权等）。外部服务可以在单元层模拟，但核心集成路径须在可控测试环境真实验证。
5. 所有测试必须可重复，不依赖生产账户或生产数据；修复不稳定测试，不能通过永久忽略来“通过”。

## 4. 每次提交的强制验证门禁

**PR/CI 基础门禁（按仓库实际技术栈配置）：**
- 静态检查、类型检查、构建及相关单元测试通过；无新引入的高严重度安全/密钥泄露问题。
- 本次变更相关的 API/契约与集成测试通过；关键路径回归测试通过。
- 检查变更文件列表及 diff，确认无意外修改；有风险的配置和迁移必须单独审查。
- 失败、未运行、环境受限或覆盖不足的测试必须逐项列明。**不得报告“全部通过”，除非实际已执行并通过。**

**发布门禁：** 在以上基础上，执行完整回归集和测试环境关键 E2E/冒烟测试；对 iOS/Android/PC 分别验证受影响的平台版本与服务端兼容性。多平台不受影响时须给出依据，而非默认认为安全。

## 5. EasyLink 必须保护的核心回归场景

以下作为长期测试清单；逐步自动化，不得声称未建成的用例已具备自动保护：

| 领域 | 核心检查 |
|---|---|
| 登录与会员 | 正常登录、错误凭证、无效/过期会员、权限变化后的状态同步 |
| SSM 授权 | 新增授权、到期撤权、续费恢复、重复下发/重复撤权、后台与节点状态一致 |
| VPN 连接 | 首次连接、切换节点、断线重连、网络变化、退出登录/失效后的权限处理 |
| 多终端兼容 | iOS、Android、PC 使用既有 API 时，不因后台变更失效 |
| 付款与回调 | 支付成功/失败、Webhook 重放、订单与会员状态幂等、异常重试（涉及变更时） |
| 网站及 SEO | 既有页面可访问、登录/支付入口可用；原有 URL、meta、正文及法律页面不被误覆盖 |

## 6. 测试环境与生产发布隔离

1. 顺序固定：**功能分支 → PR/CI → 合并审核 → 测试环境部署 → 集成/E2E/人工验收 → 用户明确批准 → 正式发布 → 发布后监控**。
2. 优先使用现有独立测试服务器（.6）和测试站验证；环境变量、数据库、SSM 节点和第三方沙箱必须与生产隔离。不得拿生产用户或生产线路进行破坏性测试。
3. 测试站通过不等于正式站授权。**任何正式发布、生产配置修改、数据库迁移、真实节点批量变更，必须有用户明确批准。**
4. 部署前留存提交 SHA、配置差异、数据库/文件备份或快照以及可执行的回滚步骤；不能可靠回滚时，必须作为风险提出并等待批准。
5. 上线后执行真实环境只读或低风险冒烟检查，检查 Sentry、服务健康、登录/确权与关键业务指标；触发严重回归时按预案停止发布或回滚，并保留现场证据。

## 7. 每次修改后必须提交“变更与回归报告”

报告中必须有以下字段，不允许空口宣布完成：

- **目标和范围**：本次修复/实现什么；明确未修改什么。
- **代码证据**：分支、commit SHA、PR、修改文件列表及关键 diff 摘要。
- **影响分析**：直接模块、跨模块/API/DB/客户端影响；兼容风险。
- **测试清单**：测试名称/命令、执行环境、实际结果（PASS/FAIL/NOT RUN）及日志位置。
- **新增回归**：Bug 复现用例、新增/更新的自动化测试及 CI 接入状态。
- **环境验证**：本地、CI、测试站、真实设备分别验证了什么，未验证什么。
- **发布状态**：仅代码完成 / 待验收 / 已批准待发布 / 已发布；无批准不得写“已上线”。
- **回滚和遗留风险**：回滚方法、Sentry/监控结果、已知缺口和待用户决定事项。

## 8. 出现失败时的处理

1. 一旦发现新回归，优先定位当前 diff 与依赖变化，保留日志和复现条件。
2. 不得用新的大范围修改掩盖之前的错误；先恢复上一个已知正确状态，或最小化修复并重新跑完整受影响测试。
3. 存在阻断级回归、缺乏必要验证、测试环境异常、回滚不可用或生产影响未评估时，停止发布并提交阻断报告。
4. 一个历史 Bug 每次复发都要检查：此前为何没有自动化测试、现有断言是否过弱、是否存在环境差异，并补齐相应保护。

**最终执行准则：一项改动只有在“目标功能正常 + 受影响旧功能正常 + 关键回归通过 + 风险已披露”时才算完成开发；只有经过测试环境验收和用户明确批准，才允许进入生产。**
